2. The Core Value Proposition (The "Why")

The Problem: India battles severe air pollution, yet citizens only receive raw numbers (e.g., "AQI 187") without context. Existing solutions do not provide personalized, health-specific advice, do not predict tomorrow's air quality, and rely on cloud services that compromise user privacy.

The AirSense Solution: A self-contained ecosystem that not only streams and forecasts pollution levels but uses a localized AI—strictly grounded in official WHO and CPCB guidelines—to answer personalized health queries without hallucinations, keeping all personal data on the user's laptop.

3. The Verified Technology Stack

No tools are included merely for complexity. Every tool solves a specific production problem.

  • Data Ingestion: WAQI API (Hourly fetches for live data).
  • Message Broker: Apache Kafka (Already running with ZooKeeper). Acts as a shock absorber between data fetching and database insertion.
  • Data Validation & DB: Pydantic (ensures data integrity) writing to TimescaleDB (PostgreSQL extension optimized for time-series data, running in Docker).
  • Machine Learning: LightGBM. Chosen over Deep Learning because it trains in seconds, handles tabular time-series flawlessly, and is fully Windows-compatible.
  • MLOps: MLflow (local file tracking) for managing model versions and retraining cycles.
  • Generative AI (RAG): ChromaDB (local vector storage) holding embedded WHO/CPCB documents, queried via LangChain and answered by Ollama running Phi-3 Mini.
  • Presentation & Alerts: Streamlit (multi-tab dashboard), Folium (interactive Gujarat/India map), Power BI (executive reporting), and a Python Telegram Bot (real-time alerts).

4. The End-to-End Workflow (No Code Overview)

  1. Ingestion: A scheduled task pings the WAQI API every hour for specified cities (e.g., Ahmedabad, Surat, Delhi) and pushes the raw JSON payload to the Kafka aqi_raw topic.
  2. Processing: A continuously running Kafka consumer reads the payload, validates it using strict rules (e.g., AQI cannot be negative), and inserts it into a TimescaleDB hypertable.
  3. Forecasting: Once a week, an automated script fetches historical data, engineers time-based features, trains a LightGBM model, logs the performance in MLflow, and saves the next 48 hours of predictions back to the database.
  4. Knowledge Retrieval (RAG): Official medical documents are pre-processed into mathematical vectors and stored locally. When a user asks a question, the system finds the most relevant paragraphs.
  5. User Interaction: The user views live charts and maps on Streamlit. They ask the chatbot a question. The system feeds the retrieved medical facts and current AQI to the local AI, which generates a safe, cited response.

6. Defense Day Backup Strategy (Zero-Fail Plan)

Technology fails during live demos. AirSense is designed to survive it:
  • Internet Goes Down: A "Replay Mode" script pushes a pre-downloaded CSV into Kafka. The entire system works identically offline.
  • GPU/AI Overheats: A UI toggle immediately disables the AI chat, freeing memory so the charts and maps continue running smoothly.
  • Docker Crashes: Static screenshots and a pre-recorded 5-minute walkthrough video are immediately available to present to the examiners.

7. The 20 Critical Directives for AI & Execution

These rules dictate exactly how the developer and the assisting AI must build this project. They are non-negotiable guidelines to ensure zero errors, zero scope creep, and 100% feasibility.

  • 1
    No Code in Planning: Do not generate massive code blocks during architectural discussions. Plan first, build module by module.
  • 2
    Respect Existing Infrastructure: The user has Kafka + ZooKeeper running on localhost:9092. Do not attempt to migrate them to KRaft. Build clients to connect to what exists.
  • 3
    Mandatory WSL2 Capping: Before deploying TimescaleDB in Docker, a `.wslconfig` file must be created to cap memory at 3GB. Failure to do this will crash the 16GB laptop.
  • 4
    VRAM Reality Check: The RTX 2050 has 4GB VRAM. Do not suggest or attempt to run LLaVA or vision models. Strictly use Phi-3 Mini (Q4 quantized) via Ollama.
  • 5
    Strict Dependency Pinning: The AI framework (LangChain) evolves rapidly. Every single library must have a strictly pinned version in `requirements.txt` to prevent sudden breakage.
  • 6
    Data Validity Over Volume: If the WAQI API returns anomalous data, it must be caught by Pydantic and logged, not forced into TimescaleDB.
  • 7
    Time-Series Validation Only: When training the LightGBM model, never use random 80/20 train/test splits. Strictly use walk-forward (chronological) validation.
  • 8
    RAG is for Safety, Not Chat: The AI is not a conversational buddy. The system prompt must force the AI to cite WHO/CPCB documents and refuse to diagnose medical conditions.
  • 9
    Mandatory Medical Disclaimers: Every AI response and every dashboard tab must feature a visible disclaimer stating this is an educational tool, not medical advice.
  • 10
    Localhost Exclusivity: Aside from fetching WAQI data and sending Telegram alerts, no data must leave the machine. The database, vector store, and LLM must be 100% local.
  • 11
    Embrace MLOps Early: Model training is not a one-off script. It must be tracked with MLflow, logging RMSE, hyperparameters, and the model artifact.
  • 12
    Champion-Challenger Promotion: The automated retraining script must only promote the new model to production if its RMSE is lower than the current active model.
  • 13
    Graceful Degradation: If a component fails (e.g., Kafka is down), the Streamlit dashboard should show a friendly "Data temporarily unavailable" error, not a giant Python traceback stack.
  • 14
    Focus on Gujarat & Major Hubs: Configure the system to track Ahmedabad, Surat, Rajkot, Gandhinagar, plus major metropolises like Delhi and Mumbai for contrast.
  • 15
    Avoid Scope Creep: Do not build mobile apps (Flutter/React Native) or IoT hardware during the 12-week core phase. These belong strictly in the "Future Enhancements" section of the report.
  • 16
    The Telegram Bot is Simple: The alerting mechanism requires only `requests.post()` to the Telegram API. Do not overcomplicate it with heavy bot frameworks.
  • 17
    Interactive Mapping is Core: Use Folium to generate the interactive map. It is lightweight, visually impressive, and integrates seamlessly into Streamlit via `streamlit-folium`.
  • 18
    Separation of Concerns: Maintain a strict folder structure: ingestion scripts separate from consumers, separate from ML training, separate from the UI.
  • 19
    Testing the Kill Switch: The AI kill-switch in the UI must actually stop querying the LLM and release resources, ensuring the system remains responsive on the 16GB laptop.
  • 20
    Simulate Defense Day Early: By Week 10, the "start_demo.bat" script must exist, capable of launching ZooKeeper, Kafka, TimescaleDB, Ollama, and Streamlit in the correct sequential order.
